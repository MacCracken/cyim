# 2026-04-25 — 0-day / CVE corpus survey for cyim

External research pass for M7. Surveys the historical CVE corpus
across vim, neovim, less, and terminal-hosted editors / pagers,
organized by *class*. For each class: the pattern, verified
representative CVEs (with primary-source citations), and cyim's
posture — *refused-by-design*, *closed*, *open* (must close before
v1.0), or *documented* (out of scope or trust-model assumed).

CVE references in this document have been verified against
primary sources (NIST NVD, MITRE, vim/neovim GitHub Security
Advisories, Red Hat / Ubuntu / SUSE security bulletins) per the
M7.5 verification pass.

Companion to [`docs/audit/2026-04-25-m7-audit.md`](../audit/2026-04-25-m7-audit.md),
which re-walks CLAUDE.md's security-hardening checklist with this
corpus in hand.

## Class 1 — Modeline RCE (config-from-content)

**Pattern:** the editor parses options or commands embedded in
file content (vim's `/* vim: set ts=4 mod:tw=80 */` modelines).
If any of the parsed options can invoke external commands or
load arbitrary configuration, opening a malicious file becomes RCE.

**Verified CVEs:**

- **[CVE-2019-12735](https://nvd.nist.gov/vuln/detail/CVE-2019-12735)**
  (vim < 8.1.1365 / neovim < 0.3.6) — `:source!` command not
  restricted by sandbox mode; modeline could trigger arbitrary OS
  commands. **CVSS v3.x 8.6 (HIGH)**, CWE-78 (OS Command
  Injection). Published 2019-06-05. Demonstrated via `execute`
  in vim and `assert_fails` / `nvim_input` in neovim.
  Mitigation: `set nomodeline`, `set modelineexpr` off, or the
  `securemodelines` plugin.
- **[CVE-2016-1248](https://www.cvedetails.com/cve/CVE-2016-1248/)**
  (vim < 8.0.0056) — vim did not properly validate values for
  `filetype`, `syntax`, and `keymap` options, allowing arbitrary
  code execution if a file with a specially crafted modeline
  was opened.
- **CVE-2002-1377** — earlier vim modeline command-execution.

**cyim posture: refused-by-design.**
cyim does not parse modelines. Configuration is `.cyimrc` only,
loaded from a known cwd-relative path. Buffer content is *never*
interpreted as configuration. Class structurally absent.

**Audit invariant:** verify no source file calls a config-parser
on buffer content. Grep for `cyimrc_load`, `_cyimrc_parse_line` —
both should only be reachable from `cyimrc_load_path` with a
path-only argument from `main.cyr` or test harnesses.

## Class 2 — Regex catastrophic backtracking (DoS)

**Pattern:** the editor ships a regex engine that uses NFA-based
backtracking. Nested quantifiers like `(a+)+b` against a long
`aaa…aaa` input run pathologically exponential. CPU-bound DoS.

**Verified CVEs:**

- **[CVE-2017-17087](https://www.cvedetails.com/cve/CVE-2017-17087/)**
  (vim < 8.0.1263) — different class technically (swap-file
  group ownership info disclosure, see Class 8) but lives in
  `fileio.c` which abuts vim's regex/buffer code. Cited in
  the regex literature for the family.

The class itself ("ReDoS") is widely documented across security
research; vim's hand-written regex engine has had multiple bugs
in this area, with patches typically arriving within days of
disclosure.

**cyim posture: refused-by-design.**
cyim's `/` `?` search uses naive byte-wise substring scan
([`src/search.cyr`](../../src/search.cyr) `_search_scan_forward` /
`_search_scan_backward`). No regex, no metacharacters. Worst case
is `O(n*m)` (typical: `O(n)`); always linear, never exponential.

**Future-proofing:** if regex search ever lands (post-v1.0
demand-gated), use a DFA-based engine (Thompson construction) —
never a backtracking NFA.

## Class 3 — Terminal escape-sequence injection

**Pattern:** buffer / file content with raw ESC bytes (0x1B) is
written to stdout verbatim. The terminal interprets the resulting
CSI sequences. Worst variants:

- Window-title manipulation (`ESC]0;TITLE\007`)
- Color palette redefinition
- xterm cursor-position readback (`ESC[6n` → terminal answers via
  stdin → editor reads as user input → composable into
  paste-as-command attacks against the parent shell on exit)

**Verified CVEs:**

- **[CVE-2013-1862](https://nvd.nist.gov/vuln/detail/CVE-2013-1862)**
  (Apache HTTP server `mod_rewrite`) — wrote data to log files
  without sanitizing non-printable characters, allowing remote
  attackers to execute arbitrary commands via escape sequences
  in terminal emulators when admins viewed the logs. Same class,
  different host program — paradigmatic example of the
  control-byte-substitution defense being load-bearing.

The class is well-known in the `cat` / `less` / `more` / vim /
TUI-editor lineage. xterm's [Control Sequences reference](https://www.x.org/docs/xterm/ctlseqs.pdf)
documents the cursor-position readback (`CSI row;column R`) and
the F3-modifier collision that's the basis for the readback
attack.

**cyim posture: closed in M6.**
[`src/render.cyr`](../../src/render.cyr) `render_ctrl_substitute`
maps control bytes (< 0x20 except Tab; plus 0x7F DEL) to `^X`
notation. ESC bytes in buffer content render as `^[`, never
reaching the terminal as a real ESC. Closed M5-audit finding F-1.

**Audit invariant:** verify both `render_build_line_naked` and
`render_build_line` route through `render_ctrl_substitute`. Test
coverage in [`tests/render.tcyr`](../../tests/render.tcyr) — 23
assertions on the `^X` substitution table.

## Class 4 — Integer overflow in command parsing

**Pattern:** integer arguments to `:set foo=N` or range operators
like `:1,5d` overflow internal counters. Typical exploit: trick
the editor into negative-loop bounds → unbounded read/write.

**Verified CVEs / Advisories:**

- **[GHSA-q22m-h7m2-9mgm](https://github.com/vim/vim/security/advisories/GHSA-q22m-h7m2-9mgm)**
  (vim) — integer overflow in `:history` command argument,
  potentially leading to use-after-free.
- **[GHSA-6g74-hr6q-pr8g](https://github.com/vim/vim/security/advisories/GHSA-6g74-hr6q-pr8g)**
  (vim < 9.0.2110) — overflow in Ex address parsing
  (e.g. `:.,$+999999999999d`). Fixed in patch 9.0.2110.
- **[GHSA-f2m2-v387-gv87](https://github.com/vim/vim/security/advisories/GHSA-f2m2-v387-gv87)**
  (vim < 9.0.2112) — overflow in `shift_line` when shifting
  in operator-pending mode with a very large count. Fixed in
  9.0.2112.

**cyim posture: bounded by i64.**
cyim's `:set tabstop=N` parses N via [`_cmd_arg_uint`](../../src/command.cyr)
which loops over digit bytes building `v = v * 10 + (c - 48)`.
For N > i64-max, `v` overflows silently. Currently the consumer
(`editor_set_cfg_tabstop`) just stores the value — no
negative-loop hazard *today* because tabstop is read but not yet
wired into a loop-bound consumer.

**Audit finding M7-1 [LOW]:** when `cfg_tabstop` becomes
load-bearing in render (the line-number gutter, tab expansion),
bound it at parse time to a reasonable max (e.g., 32). cyim's
own ex-address-style parsing should pre-emptively cap arithmetic
to avoid the GHSA-6g74-hr6q-pr8g class. Tracked in audit doc.

## Class 5 — Embedded scripting sandbox escapes

**Pattern:** Vimscript / Lua / Python plugins offered as a
sandboxed extension surface. Sandbox escapes via `os.execute`,
`io.popen`, fdopen tricks, or the language's reflection /
metatable hacks.

**Verified CVEs:**

- **[CVE-2008-2712](https://www.cvedetails.com/cve/CVE-2008-2712/)**
  (vim 7.1.314, 6.4 and others) — vim shipped multiple bundled
  Vimscript files (`filetype.vim`, `xpm.vim`, `gzip_vim`,
  `netrw`) that called `execute()` and `system()` without
  sanitizing inputs. User opens a crafted file → arbitrary
  command execution as the user. The "scripting layer let me
  do something the editor's privilege should have prevented"
  pattern in its purest form.
- **[CVE-2022-0543](https://ine.com/blog/cve-20220543-lua-sandbox-escape-in-redis)**
  (Redis Lua sandbox escape; not vim/nvim but exemplary of the
  Lua sandbox class) — illustrates why Lua's whitelist-based
  sandbox is fundamentally fragile.
- **[neovim treesitter language-name path-traversal advisory](https://github.com/neovim/neovim/security/advisories/GHSA-6f9m-hj8h-xjgj)** —
  neovim concatenated the language name into a shared-library
  path without sanitizing, allowing path traversal to load a
  malicious shared object and execute arbitrary commands.

**cyim posture: refused-by-design.**
cyim has no embedded scripting language. Configuration is data
(`.cyimrc`, vyakarana `.cyml` grammars) — both *parsed*, never
*executed*. Plugin system is a Refusal §0 non-goal. Class
structurally absent.

This is the load-bearing security refusal. The CVE-2008-2712
pattern alone would require auditing every bundled Vimscript
helper for input-sanitization correctness; cyim sidesteps the
whole class by not having the surface.

## Class 6 — Plugin loading / supply-chain attacks

**Pattern:** the editor loads plugins or grammars from a search
path. An attacker who can write to one of those paths (often XDG
dirs) substitutes a malicious plugin. The plugin runs at editor
startup with the user's privileges.

**Verified examples:**

- **[neovim treesitter advisory GHSA-6f9m-hj8h-xjgj](https://github.com/neovim/neovim/security/advisories/GHSA-6f9m-hj8h-xjgj)** —
  the language-name path-traversal cited in Class 5 is also a
  supply-chain shape: a malicious treesitter grammar package
  could leverage it.

The class is well-documented in the security best-practices
literature even where specific CVE numbers are sparse —
"your dotfiles repo got owned and the cleanup script pulled
before you reviewed" is the modern variant.

**cyim posture: bundled-only today; documented for future overlays.**

cyim loads grammars from `/proc/self/exe`-relative `grammars/`
(see [`src/highlight.cyr`](../../src/highlight.cyr)
`_hl_resolve_dir`). The grammars are checked into the cyim repo
and shipped with the binary. No user-supplied grammar overlay
path exists today.

When user-grammar overlays land (planned per
[`docs/guides/cyimrc.md`](../guides/cyimrc.md), deferred):

- Grammars are *data*, not code. A malicious `.cyml` can
  mistokenize but cannot execute. Worst case: a security-relevant
  string (`if (auth == "admin")`) gets mistokenized as a comment
  and the user's eyes skip it. **MEDIUM** risk in adversarial
  environments.
- Document the trust model: user-config dirs are user-controlled,
  same risk profile as `.bashrc`. Don't run cyim with elevated
  privileges. Document in the user-grammar overlay bite when it
  lands.

**Audit finding M7-2 [LOW, deferred]:** when overlays land, the
overlay-load path needs an explicit trust note in the user-facing
docs.

## Class 7 — Large-input DoS (memory exhaustion)

**Pattern:** open a multi-GB file → editor allocates entire
content in memory → OOM kill. Often combined with allocator
pathologies (slow grow-to-fit loops).

**Class shape:** general DoS pattern. Local editors mostly hit
it as a usability issue (open a 10 GB log, system swaps) rather
than as a directed attack — because by definition you have to
choose what to open. CVE numbers are sparse in this class
because it's typically considered a usability bug rather than a
security bug; still worth bounding for "I accidentally piped a
giant build log into a file and `:e`d it" scenarios.

**cyim posture: closed in M7.**

[`src/buffer.cyr`](../../src/buffer.cyr) `buf_load_file` reads
in 4 KB chunks into a gap-buffer that auto-grows by doubling. No
size cap previously. Opening a 100 GB file would attempt to
allocate 100 GB+, hitting brk failure or OOM.

**M7 fix (this milestone, bite 3):** added `cfg_max_filesize`
(default 100 MB) on the editor state plus `:set maxfilesize=N`
runtime toggle. `:e <path>` now stats the file via
`lseek(SEEK_END)` before allocating any buffer; refuses with
new `ERR_FILE_TOO_LARGE` if size > cap. Closes M5-audit F-2;
9 new regression tests in `tests/command.tcyr` cover the
threshold, raise-and-retry, and `:set maxfilesize=N` paths.

## Class 8 — TOCTOU on swap / save files

**Pattern:** the editor opens a file, holds the path string,
then re-opens or writes through the same path string later. An
attacker swaps the file via symlink or rename in between — the
save lands in the wrong place, often with elevated permissions.

**Verified CVEs:**

- **[CVE-2017-17087](https://www.cvedetails.com/cve/CVE-2017-17087/)**
  (vim < 8.0.1263) — vim sets the group ownership of a `.swp`
  file to the editor's primary group, which may differ from
  the source file's group. Information disclosure: editing
  `/etc/shadow` (root:shadow mode 0640) creates
  `/etc/.shadow.swp` (root:users mode 0640), readable by any
  user in `users`. Strictly a permissions / info-disclosure
  bug, but lives in the same `fileio.c` race-territory.
- **[CVE-2017-1000382](https://www.cvedetails.com/cve/CVE-2017-1000382/)**
  (vim 8.0.1187+) — vim ignored umask when creating swap
  files; restricted-mode bypass.
- **vim 5.x swap-file race condition** ([Exploit-DB 20967](https://www.exploit-db.com/exploits/20967),
  Bugtraq BID 2927) — symlink-target attack against vim's swap
  file naming. By conjecturing the swap-file name for a file
  another user is editing, a local user could create a malicious
  symlink to a non-existent file, causing the new target to be
  created with the privileges of the user running vim. Classic
  TOCTOU shape.

**cyim posture: standard POSIX semantics; documented per
[ADR 0001](../adr/0001-trust-model.md).**

cyim's `:e <path>` reads the file at open time; the content is
held in the gap-buffer. Subsequent symlink swaps don't affect
the in-memory buffer.

`:w` opens the *same path string* with `O_WRONLY | O_CREAT |
O_TRUNC` and writes. If the path now points to a different file
(via symlink swap), the write follows the symlink. Vim's
default behavior is the same.

**Mitigation considered but not adopted:** open-once-on-load
and hold the fd; save via writing back through the same fd. Adds
file-handle pressure; not worth the complexity for cyim's
threat model (interactive local user, not setuid).

**Audit finding M7-3 [LOW, accepted]:** TOCTOU is documented as
"matches vim's threat model." If cyim ever ships a setuid mode,
this becomes a real concern; today's binary is non-privileged.

(cyim doesn't create swap files; M5-audit's hot-reload /
crash-recovery scope deferred to post-v1.0. The CVE-2017-17087
permissions issue is therefore N/A — there's no swap file to
mis-permission.)

## Class 9 — Format-string vulnerabilities

**Pattern:** user input passed to a `printf`-family function as
the format string itself (`printf(user_input)` instead of
`printf("%s", user_input)`). Allows arbitrary memory read/write
via `%n` and friends. The vim variant has been
expression-injection: format-string-like syntax (`%{expr}`) gets
*evaluated* as Vimscript, not just printed.

**Verified CVE / Advisory:**

- **[GHSA-2gmj-rpqf-pxvh / CVE-2026-34714](https://github.com/vim/vim/security/advisories/GHSA-2gmj-rpqf-pxvh)**
  (vim 9.1.1390 < x < 9.2.0272) — `%{expr}` injection in the
  tabpanel statusline feature. The tabpanel option lacked the
  `P_MLE` (Prevent Modeline Expressions) security flag; a
  crafted file could trigger expression evaluation, and since
  Vimscript can invoke shell commands via `system()`, this
  enabled arbitrary code execution. Fixed in 9.2.0272.

This is an interesting overlap — Vim's "format strings" aren't
quite C's printf format strings, but the injection shape is the
same: untrusted input flows into a context that interprets
metacharacters.

**cyim posture: refused-by-design.**

cyim doesn't use format strings. All output is direct byte
writes via `syscall(1, 1, ptr, len)`. No `%`-interpretation
anywhere in the editor's output path. `fmt.cyr` (stdlib) does
have `fmt_int` etc., but those take an integer argument and
emit fixed sequences — not format strings in the C sense.

cyim has no expression-evaluation feature analogous to
Vimscript's `%{expr}` — the GHSA-2gmj-rpqf-pxvh class is
structurally absent (Class 5 refusal cascading into Class 9).

## Class 10 — Bracketed-paste-as-command attacks

**Pattern:** terminal supports bracketed-paste mode. A malicious
file contains escape sequences that disable bracketed paste,
then inject text as if the user typed it. When the editor
exits, the user's shell receives the injected text as a
command.

**Verified examples:**

- **[CVE-2017-8386](https://insinuator.net/2017/05/git-shell-bypass-by-abusing-less-cve-2017-8386/)**
  (git-shell + less) — git-shell could be abused to achieve
  arbitrary file read, directory listing, and somewhat
  restricted file write through the `less` pager. When
  `--help` is passed to git commands, less is invoked in
  interactive mode (auto-enabled when a pty is available),
  and less's `!`, `e`, `s` commands give shell-equivalent
  capabilities. Same class shape: untrusted byte stream
  reaches a tool that emits terminal-control side effects.
- General "[Terminal Escape Injection](https://www.infosecmatter.com/terminal-escape-injection/)"
  literature — multiple advisories around 2017–2019 across
  the cat/less/more/cli-tool family. The escape-sequence
  family lives at [CWE-150](https://cwe.mitre.org/data/definitions/150.html).

**cyim posture: closed in M6 (companion to Class 3).**

Same fix as Class 3 — `render_ctrl_substitute` strips ESC
bytes. Without ESC, the terminal can't be tricked into
bracketed-paste disable / re-enable cycles.

## Class 11 — Path traversal in file operations

**Pattern:** user provides a path; editor doesn't normalize or
restrict it; reads/writes outside the intended scope.

**Class shape:** common in network-accessible tools, less
relevant for local interactive editors. The vulnerability shape
is "user-supplied path lets the program escape its intended
filesystem scope" — which only matters if there *is* an
intended scope (chroot, sandbox, restricted mode). Open-anywhere
editors inherit the user's privileges and aren't a privilege
boundary.

CVE numbers in this class for editors are sparse precisely
because there's no "intended scope" to escape from. Path
traversal becomes a real CVE in setuid / containerized / web-
accessible editor variants.

**cyim posture: documented per
[ADR 0001](../adr/0001-trust-model.md); trust model =
"interactive local user".**

`:e <path>` accepts arbitrary paths, including `../` and
absolute paths. This matches vim. The user already has shell
access; cyim is not a privilege boundary.

**Audit finding M7-4 [LOW, accepted]:** documented in ADR 0001.
Future restricted-mode work (daimon-driven sandbox per the
consumer roadmap) inherits the question; the ADR explicitly
flags it as needing a follow-up ADR if/when that lands.

## Class 12 — Memory-corruption via crafted input

**Pattern:** off-by-one, integer-truncation, or sign-confusion
in buffer-bounds checks lets crafted input write past
allocation. The classic "exploit primitive" for editors.

**Verified CVEs (heavily represented in vim's recent history):**

- **[CVE-2023-4738](https://nvd.nist.gov/vuln/detail/CVE-2023-4738)**
  (vim < 9.0.1848) — heap-based buffer overflow in
  `vim_regsub_both()`, the regex-substitution engine.
  **CVSS v3.1 7.8 (HIGH)**, CWE-787 (Out-of-bounds Write) +
  CWE-122 (Heap-based Buffer Overflow). Published 2023-09-02.
  Local-attack vector with user interaction (open crafted file).
- **CVE-2022-0413** (vim < 8.2) — use-after-free in the
  substitute command when used with a function call.
- **CVE-2022-0351** (vim < 8.2.4437) — heap-based buffer
  overflow.
- **CVE-2021-3778** (vim) — use-after-free in spell checking.
- **CVE-2022-2980** (vim) — memory-handling bug when opening
  certain files.
- **[CVE-2025-22134](https://www.sentinelone.com/vulnerability-database/cve-2025-22134/)**
  (vim) — buffer overflow.

The pattern repeats yearly in vim's CVE history — the
hand-written regex engine and the C-language buffer code
together produce a steady drip of OOB writes / UAFs / heap
overflows.

**cyim posture: closed-by-construction; tested.**

cyim's gap-buffer (`src/buffer.cyr`) does explicit bounds checks
at every public op. The header is 64 bytes, accessed via fixed
offsets — no pointer arithmetic on attacker-controlled values.

**Test coverage:** [`tests/buffer.tcyr`](../../tests/buffer.tcyr)
(47 assertions), [`tests/motion.tcyr`](../../tests/motion.tcyr)
(87 assertions covering line-coord boundaries),
[`fuzz/buffer.fcyr`](../../fuzz/buffer.fcyr) (10 K random ops,
every iteration asserts cursor + buf_len invariants).

`var buf[N]` declarations in the codebase reviewed in M5-audit
(F-1 group). Every static-size buffer matches its consumer's
expected max input. No unbounded `memcpy`-style operations.

cyim doesn't have a regex engine (Class 2 refused), so the
CVE-2023-4738 / vim_regsub_both pattern can't recur here.

## Class 13 — Multi-byte / Unicode parsing bugs

**Pattern:** UTF-8 multi-byte sequences with invalid continuation
bytes get mishandled. Editor treats invalid input as if it were
valid, leading to display corruption or crash.

**Class shape:** vim has had encoding-related CVEs over the
years; the general pattern is well-documented in any
text-handling tool. The exploitation primitive is usually a
length / index calculation that assumes well-formed UTF-8.

**cyim posture: byte-oriented; UTF-8 sequences pass through
verbatim.**

cyim treats the buffer as a byte stream. There's no UTF-8
decoding layer; multi-byte glyphs render as multi-byte sequences
(terminal handles the display width). No way to corrupt internal
state via malformed UTF-8 because cyim doesn't *parse* UTF-8.

**Caveat:** column-counting in motions (`buf_col_of`,
`motion_*`) uses byte offsets, not glyph offsets. A line with a
3-byte UTF-8 character has column 3 at byte 3, even though the
user sees one glyph. This is intentional for v1.0 (matches
vim's default behavior with `:set encoding=latin1`); proper
Unicode-aware column counting is post-v1.0 demand-gated.

**Audit finding M7-5 [LOW, documented]:** byte-vs-glyph column
distinction documented in
[`docs/guides/usage.md`](../guides/usage.md) "Troubleshooting".

## Summary

cyim's threat model is dominated by *what the editor refuses to
do*:

| Class | Pattern | cyim posture |
|-------|---------|--------------|
| 1     | Modeline RCE                  | refused-by-design |
| 2     | Regex backtracking            | refused-by-design |
| 3     | Terminal escape injection     | **closed** (M6 F-1 fix) |
| 4     | Integer overflow              | bounded by i64; **M7-1 [LOW]** for tabstop loop-bound |
| 5     | Scripting sandbox escapes     | refused-by-design |
| 6     | Plugin / supply-chain         | bundled-only; **M7-2 [LOW, deferred]** for future overlays |
| 7     | Large-input DoS               | **closed** (M7 F-2 fix) |
| 8     | TOCTOU on save                | **M7-3 [LOW, accepted]** ADR 0001 |
| 9     | Format-string                 | refused-by-design |
| 10    | Paste-as-command              | **closed** (M6 F-1 fix, companion to Class 3) |
| 11    | Path traversal                | **M7-4 [LOW, accepted]** ADR 0001 |
| 12    | Memory corruption             | closed-by-construction; tested + fuzzed |
| 13    | Unicode parsing               | refused-by-design (byte-oriented); **M7-5 [LOW, documented]** |

**Net position pre-v1.0:**

- **5 classes structurally refused** (no surface to attack:
  Classes 1, 2, 5, 9, 13)
- **3 classes closed by implementation** (defended in code:
  Classes 3, 10, 12)
- **1 class fixed in M7** (Class 7 → F-2 → `:e` size cap)
- **4 classes documented as accepted** at the trust-model level
  (Classes 4, 6, 8, 11)

**v1.0 gating:**

- 0 CRITICAL / HIGH findings remain at end of M7
- All 5 LOW findings (M7-1 through M7-5) tracked with explicit
  rationale; none block v1.0

**The big win from refusal §0:** the bulk of vim's historical CVE
surface — modeline RCE (CVE-2019-12735, CVE-2016-1248,
CVE-2002-1377), Vimscript injection (CVE-2008-2712), tabpanel
expression evaluation (CVE-2026-34714), and the plugin /
supply-chain class — is *structurally absent* in cyim. Not
because we found and fixed bugs there, but because there's no
attack surface. The historical CVE corpus on vim is dominated
by classes that don't apply to cyim's design.

The remaining classes that *could* apply (memory corruption,
escape injection, integer overflow, large-input DoS) are either
closed-by-construction (gap-buffer bounds-checks, no regex
engine), defended in code (M6 control-byte substitution, M7
size cap), or documented per the explicit trust model (TOCTOU,
path traversal — interactive-local-user only).
