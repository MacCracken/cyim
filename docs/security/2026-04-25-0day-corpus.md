Surveys the historical CVE corpus across vim, neovim, and
terminal-hosted editors / pagers, organized by *class*. For each
class: the pattern, the kind of CVEs that exemplify it, and cyim's
posture — *refused-by-design*, *closed*, *open* (must close before
v1.0), or *documented* (out of scope or trust-model assumed).

## Class 1 — Modeline RCE (config-from-content)

**Pattern:** the editor parses options or commands embedded in file
content (vim's `:set ts=4 mod:tw=80` modelines). If any of the parsed
options can invoke external commands or load arbitrary configuration,
opening a malicious file becomes RCE.

**Class shape:** vim's modeline parser has historically had
modeline-via-buffer-content RCE bugs across multiple major
versions; the pattern is "config setting embedded in file →
parser invokes shell." Defenses have included disabling
dangerous options in modelines and dropping modeline parsing
entirely in restricted modes.

*(M7.5: verify specific vim modeline CVEs against MITRE/NVD —
expected to find 3+ in the 2002–2019 range.)*

**cyim posture: refused-by-design.**
cyim does not parse modelines. Configuration is `.cyimrc` only,
loaded from a known cwd-relative path. Buffer content is *never*
interpreted as configuration. Class structurally absent.

**Audit invariant:** verify no source file calls a config-parser on
buffer content. Grep for `cyimrc_load`, `_cyimrc_parse_line` — both
should only be reachable from `cyimrc_load_path` with a path-only
argument from `main.cyr` or test harnesses.

## Class 2 — Regex catastrophic backtracking (DoS)

**Pattern:** the editor ships a regex engine that uses NFA-based
backtracking (vim's hand-written engine, BRE/ERE-style). Nested
quantifiers like `(a+)+b` against an `aaa…aaa` input go pathologically
exponential. CPU-bound DoS.

**Class shape:** ReDoS is a well-documented class. Vim ships a
hand-written regex engine with NFA-style backtracking; complex
patterns against pathological inputs spike CPU. Pure linear-time
scanners (DFA-based, or naive substring) sidestep the class
entirely.

*(M7.5: verify specific vim regex CVEs against the corpus — the
class is real, the specific numbers cited need primary-source
confirmation.)*

**cyim posture: refused-by-design.**
cyim's `/` `?` search uses naive byte-wise substring scan
([`src/search.cyr`](../../src/search.cyr) `_search_scan_forward` /
`_search_scan_backward`). No regex, no metacharacters. Worst case
is `O(n*m)` (typical: `O(n)`); always linear, never exponential.

**Future-proofing:** if regex search ever lands (post-v1.0
demand-gated), use a DFA-based engine (Thompson construction) — never
a backtracking NFA.

## Class 3 — Terminal escape-sequence injection

**Pattern:** buffer / file content with raw ESC bytes (0x1B) is
written to stdout verbatim. The terminal interprets the resulting
CSI sequences. Worst variants:

- Window-title manipulation (`ESC]0;TITLE\007`)
- Color palette redefinition
- xterm cursor-position readback (`ESC[6n` → terminal answers via
  stdin → editor reads as user input → composable into
  paste-as-command attacks against the parent shell on exit)

**Class shape:** any tool that prints buffer content to a terminal
without sanitizing control bytes is a candidate. The historic
literature spans vim, less, more, cat, and (more recently)
modern terminal-hosted editors / TUIs. The xterm
cursor-position-readback variant (`ESC[6n` → reply via stdin →
read as user input) is the worst flavor — it composes with
paste-as-command for pivot to shell.

*(M7.5: verify specific vim and less CVE references against
NVD; the class has multiple real entries in the 2008–2019
range.)*

**cyim posture: closed in M6.**
[`src/render.cyr`](../../src/render.cyr) `render_ctrl_substitute`
maps control bytes (< 0x20 except Tab; plus 0x7F DEL) to `^X`
notation. ESC bytes in buffer content render as `^[`, never reaching
the terminal as a real ESC. Closed M5-audit finding F-1.

**Audit invariant:** verify both `render_build_line_naked` and
`render_build_line` route through `render_ctrl_substitute`. Test
coverage in [`tests/render.tcyr`](../../tests/render.tcyr) — 23
assertions on the `^X` substitution table.

## Class 4 — Integer overflow in command parsing

**Pattern:** integer arguments to `:set foo=N` or range operators
like `:1,5d` overflow internal counters. Typical exploit: trick the
editor into negative-loop bounds → unbounded read/write.

**Class shape:** any C codebase parsing user-supplied integer
arguments without explicit bounding can overflow internal
counters. The exploitation primitive is usually
"trick a length / index check into a negative comparison →
unbounded read or write." Vim has had several CVEs in this class
across Ex-mode parsing.

*(M7.5: verify against the corpus.)*

**cyim posture: bounded by i64.**
cyim's `:set tabstop=N` parses N via [`_cmd_arg_uint`](../../src/command.cyr)
which loops over digit bytes building `v = v * 10 + (c - 48)`. For
N > i64-max, `v` overflows silently. Currently the consumer
(`editor_set_cfg_tabstop`) just stores the value — no negative-loop
hazard *today* because tabstop is read but not yet wired into a
loop-bound consumer.

**Audit finding M7-1 [LOW]:** when `cfg_tabstop` becomes load-bearing
in render (line-number gutter, tab expansion), bound it at parse
time to a reasonable max (e.g., 32). Tracked in audit doc.

## Class 5 — Embedded scripting sandbox escapes

**Pattern:** Vimscript / Lua / Python plugins offered as a sandboxed
extension surface. Sandbox escapes via `os.execute`, `io.popen`,
fdopen tricks, or the language's reflection / metatable hacks.

**Class shape:** "the scripting layer let me do something the
editor's privilege should have prevented" — the dominant
pattern across vim/neovim CVEs of the last decade. Lua's
whitelist-based sandbox is fundamentally fragile (every
"convenience" stdlib addition is a potential escape). Vimscript
has had its own family of issues around `:source`,
`feedkeys()`, autocmd composition, and friends.

*(M7.5: verify neovim Lua CVEs and vim Vimscript CVEs against
the corpus. Class is well-documented; specific numbers need
sourcing.)*

**cyim posture: refused-by-design.**
cyim has no embedded scripting language. Configuration is data
(`.cyimrc`, vyakarana `.cyml` grammars) — both are *parsed*, never
*executed*. Plugin system is a Refusal §0 non-goal. Class
structurally absent.

This is the load-bearing security refusal. Most vim/neovim CVEs of
the last decade reduce to "the scripting layer let me do something
the editor's privilege should have prevented." cyim doesn't have a
scripting layer.

## Class 6 — Plugin loading / supply-chain attacks

**Pattern:** the editor loads plugins or grammars from a search path.
An attacker who can write to one of those paths (often XDG dirs)
substitutes a malicious plugin. The plugin runs at editor startup
with the user's privileges.

**Class shape:** plugin systems load arbitrary code from
search paths the user controls but doesn't always inspect. The
modern variant is "your dotfiles repo got owned and the
cleanup script pulled before you reviewed." Distinct from
sandbox escapes (Class 5) — supply-chain compromise doesn't
need a sandbox to escape; it just runs as the user.

*(M7.5: verify; this class is more "documented best practice"
than a specific-CVE class for editors.)*

**cyim posture: bundled-only today; documented for future overlays.**

cyim loads grammars from `/proc/self/exe`-relative `grammars/`
(see [`src/highlight.cyr`](../../src/highlight.cyr) `_hl_resolve_dir`).
The grammars are checked into the cyim repo and shipped with the
binary. No user-supplied grammar overlay path exists today.

When user-grammar overlays land (planned per
[`docs/guides/cyimrc.md`](../guides/cyimrc.md), deferred):

- Grammars are *data*, not code. A malicious `.cyml` can mistokenize
  but cannot execute. Worst case: a security-relevant string
  (`if (auth == "admin")`) gets mistokenized as a comment and the
  user's eyes skip it. **MEDIUM** risk in adversarial environments.
- Document the trust model: user-config dirs are user-controlled,
  same risk profile as `.bashrc`. Don't run cyim with elevated
  privileges. Document in the user-grammar overlay bite when it lands.

**Audit finding M7-2 [LOW, deferred]:** when overlays land, the
overlay-load path needs an explicit trust note in the user-facing
docs.

## Class 7 — Large-input DoS (memory exhaustion)

**Pattern:** open a multi-GB file → editor allocates entire content
in memory → OOM kill. Often combined with allocator pathologies
(slow grow-to-fit loops).

**Class shape:** general DoS pattern. Local editors mostly hit
it as a usability issue (open a 10 GB log, system swaps) rather
than as a directed attack — because by definition you have to
choose what to open. Still worth bounding for "I accidentally
piped a giant build log into a file and `:e`d it" scenarios.

*(M7.5: less critical to verify — class is well-known
without needing a specific CVE.)*

**cyim posture: open. M5-audit F-2.**

[`src/buffer.cyr`](../../src/buffer.cyr) `buf_load_file` reads in
4 KB chunks into a gap-buffer that auto-grows by doubling. No
size cap. Opening a 100 GB file would attempt to allocate 100 GB+,
hitting brk failure or OOM.

**M7 fix (in this milestone):** add `:set maxfilesize=N` (default
~100 MB); `:e <path>` stats the file first and refuses with
`ERR_FILE_TOO_LARGE` if the size exceeds the cap. Override via
`:e!` (force) — matches vim's `:edit!` semantic for "I really
mean it."

## Class 8 — TOCTOU on file save

**Pattern:** the editor opens a file, user edits, saves. Between
open and save, an attacker swaps the file via symlink or rename —
the save lands in the wrong place, often with elevated permissions.

**Class shape:** classic file-system race in any tool that
opens a file by path, holds the path string, and re-opens or
writes through the same path string later. Severity scales
with privilege — historically much worse for setuid editors;
for non-privileged interactive editors like cyim, it's
"document the assumption."

*(M7.5: verify vim file-rename CVEs against the corpus.)*

**cyim posture: standard POSIX semantics; documented.**

cyim's `:e <path>` reads the file at open time; the content is held
in the gap-buffer. Subsequent symlink swaps don't affect the
in-memory buffer.

`:w` opens the *same path string* with `O_WRONLY | O_CREAT | O_TRUNC`
and writes. If the path now points to a different file (via symlink
swap), the write follows the symlink. Vim's default behavior is the
same.

**Mitigation considered but not adopted:** open-once-on-load and
hold the fd; save via writing back through the same fd. Adds
file-handle pressure; not worth the complexity for cyim's threat
model (interactive local user, not setuid).

**Audit finding M7-3 [LOW, accepted]:** TOCTOU is documented as
"matches vim's threat model." If cyim ever ships a setuid mode,
this becomes a real concern; today's binary is non-privileged.

## Class 9 — Format-string vulnerabilities

**Pattern:** user input passed to a `printf`-family function as the
format string itself (`printf(user_input)` instead of
`printf("%s", user_input)`). Allows arbitrary memory read/write.

**Class shape:** classic C vuln. Mostly extinct in modern
codebases that use static analysis or `printf("%s", ...)`
discipline. Vim's history has format-string issues mostly
in error-reporting paths.

*(M7.5: verify vim format-string CVEs; class is well-known
but specific numbers need sourcing.)*

**cyim posture: refused-by-design.**

cyim doesn't use format strings. All output is direct byte writes
via `syscall(1, 1, ptr, len)`. No `%`-interpretation anywhere in
the editor's output path. Class structurally absent.

`fmt.cyr` (stdlib) does have `fmt_int` etc., but those take an
integer argument and emit fixed sequences — not format strings in
the C sense.

## Class 10 — Bracketed-paste-as-command attacks

**Pattern:** terminal supports bracketed-paste mode. A malicious
file contains escape sequences that disable bracketed paste, then
inject text as if the user typed it. When the editor exits, the
user's shell receives the injected text as a command. Recent CVE
class (~2019+).

**Class shape:** specific to xterm + bracketed-paste-aware
shells. Recent CVE class (~2019+) — multiple advisories across
less / cat / similar tools. The pivot is shell-side: when the
editor exits and shell takes over the TTY, the injected text
arrives as an unbracketed paste and runs as if typed.

*(M7.5: verify the less CVE specifically; class itself is
well-documented in 2019+ security advisories.)*

**cyim posture: closed in M6 (companion to Class 3).**

Same fix as Class 3 — `render_ctrl_substitute` strips ESC bytes.
Without ESC, the terminal can't be tricked into bracketed-paste
disable / re-enable cycles.

## Class 11 — Path traversal in file operations

**Pattern:** user provides a path; editor doesn't normalize or
restrict it; reads/writes outside the intended scope.

**Class shape:** common in network-accessible tools, less
relevant for local interactive editors. The vulnerability shape
is "user-supplied path lets the program escape its intended
filesystem scope" — which only matters if there *is* an intended
scope (chroot, sandbox, restricted mode). Open-anywhere editors
inherit the user's privileges and aren't a privilege boundary.

**cyim posture: documented; trust model = "interactive local user".**

`:e <path>` accepts arbitrary paths, including `../` and absolute
paths. This matches vim. The user already has shell access; cyim is
not a privilege boundary.

**Audit finding M7-4 [LOW, accepted; ADR pending]:** document the
trust model in `docs/adr/` so future restricted-mode work
(daimon-driven sandbox per the consumer roadmap) inherits the
question explicitly. Until then, cyim operates with the invoking
user's privilege; no path validation.

## Class 12 — Memory-corruption via crafted input

**Pattern:** off-by-one, integer-truncation, or sign-confusion in
buffer-bounds checks lets crafted input write past allocation. The
classic "exploit primitive" for editors.

**Class shape:** the workhorse class. Every interesting editor
exploit primitive in C-language editors traces back to one of
these patterns in buffer/regex/parser code. Vim has a long
history here — many of its security releases over the years
have closed memory-corruption bugs in the regex engine
specifically.

*(M7.5: verify specific vim memory-corruption CVEs; class is
heavily represented in NVD for vim.)*

**cyim posture: closed-by-construction; tested.**

cyim's gap-buffer (`src/buffer.cyr`) does explicit bounds checks at
every public op. The header is 64 bytes, accessed via fixed offsets
— no pointer arithmetic on attacker-controlled values.

**Test coverage:** [`tests/buffer.tcyr`](../../tests/buffer.tcyr) (47
assertions), [`tests/motion.tcyr`](../../tests/motion.tcyr) (87
assertions covering line-coord boundaries),
[`fuzz/buffer.fcyr`](../../fuzz/buffer.fcyr) (10K random ops, every
iteration asserts cursor + buf_len invariants).

`var buf[N]` declarations in the codebase reviewed in M5-audit
(F-1 group). Every static-size buffer matches its consumer's
expected max input. No unbounded `memcpy`-style operations.

## Class 13 — Multi-byte / Unicode parsing bugs

**Pattern:** UTF-8 multi-byte sequences with invalid continuation
bytes get mishandled. Editor treats invalid input as if it were
valid, leading to display corruption or worse (crash, info leak).

**Class shape:** any tool that decodes UTF-8 (or other variable-
width encoding) into internal char positions can mis-handle
malformed sequences. Vim has had encoding-related CVEs over
the years across multibyte support paths. Pure byte-oriented
tools sidestep the class.

*(M7.5: verify; class is real but vim-specific numbers need
sourcing.)*

**cyim posture: byte-oriented; UTF-8 sequences pass through
verbatim.**

cyim treats the buffer as a byte stream. There's no UTF-8 decoding
layer; multi-byte glyphs render as multi-byte sequences (terminal
handles the display width). No way to corrupt internal state via
malformed UTF-8 because cyim doesn't *parse* UTF-8.

**Caveat:** column-counting in motions (`buf_col_of`, `motion_*`)
uses byte offsets, not glyph offsets. A line with a 3-byte UTF-8
character has column 3 at byte 3, even though the user sees one
glyph. This is intentional for v1.0 (matches vim's default
behavior with `:set encoding=latin1`); proper Unicode-aware column
counting is post-v1.0 demand-gated.

**Audit finding M7-5 [LOW, documented]:** byte-vs-glyph column
distinction needs a doc note in [`docs/guides/usage.md`](../guides/usage.md).

## Summary

cyim's threat model is dominated by *what the editor refuses to do*:

| Class | Pattern | cyim posture |
|-------|---------|--------------|
| 1     | Modeline RCE                  | refused-by-design |
| 2     | Regex backtracking            | refused-by-design |
| 3     | Terminal escape injection     | **closed** (M6 F-1 fix) |
| 4     | Integer overflow              | bounded by i64; **M7-1 [LOW]** for tabstop loop-bound |
| 5     | Scripting sandbox escapes     | refused-by-design |
| 6     | Plugin / supply-chain         | bundled-only; **M7-2 [LOW, deferred]** for future overlays |
| 7     | Large-input DoS               | **M7 fix in bite 3** (was F-2) |
| 8     | TOCTOU on save                | **M7-3 [LOW, accepted]** matches vim model |
| 9     | Format-string                 | refused-by-design |
| 10    | Paste-as-command              | **closed** (M6 F-1 fix) |
| 11    | Path traversal                | **M7-4 [LOW, accepted]** trust model documented |
| 12    | Memory corruption             | closed-by-construction; tested + fuzzed |
| 13    | Unicode parsing               | refused-by-design (byte-oriented); **M7-5 [LOW, documented]** for col-counting |

**Net position pre-v1.0:**

- 5 classes structurally refused (no surface to attack)
- 3 classes closed by implementation (defended in code)
- 1 class fixed in M7 (Class 7 → F-2)
- 4 classes documented as accepted at the trust-model level

**v1.0 gating:**

- 0 CRITICAL / HIGH findings remain at end of M7
- All 5 LOW findings (M7-1 through M7-5) tracked with explicit
  rationale; none block v1.0
