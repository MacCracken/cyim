## Method, and why the first pass found nothing

The scan that opened this audit — "every `var NAME[N]` accessed with
`load64`/`store64`, checked against its maximum written offset" — is the
same one that cleared cyim's tree during the 1.8.2 investigation of
BUG-002, and it returned **zero findings** again. That scan was looking
for the shape of a bug already known (`cyim-lsp`'s `var argv[4]`).

Every finding below came from a different question, asked per data path
rather than per syntax pattern:

> **Where does a value from outside the process reach a fixed-size buffer,
> a loop bound, or a length calculation — and what is the *stated* domain
> of that value at each hop?**

The three inputs that answer it are the terminal (geometry), the current
directory (`.cyimrc`), and the kernel (syscall returns). F-1 came from
the third, F-2 from the second, F-3 from the first.

## 3. Findings

### F-1 — `buf_save_file` reports a short write as success (**HIGH**) — FIXED

**Every write path in cyim could silently destroy most of a file and
report success**: `:w`, `:wq`, `cyim --write`, `--replace`,
`--replace-all`, `--batch`, `--replace-files[-all]`, and the agnos line
editor all funnel through `buf_save_file`.

`write(2)` is permitted to transfer **fewer bytes than requested and
report that count as success** — under `ENOSPC`, under `RLIMIT_FSIZE`,
or when a signal lands after a partial transfer. The pre-1.8.3 code
called `file_write` once per gap segment, tested only `< 0`, and
returned the short count as a **positive** value:

```cyrius
var n1 = file_write(fd, data, gs);
if (n1 < 0) { file_close(fd); return n1; }
total = total + n1;          # <-- a SHORT write lands here as success
```

Every caller tests `< 0`, so a short write cleared the modified flag in
the editor and exited **0** in the CLI.

**Measured before the fix**, 575-byte payload, `RLIMIT_FSIZE` = 100 bytes:

| verb | exit code | bytes on disk | bytes lost |
|---|---:|---:|---:|
| `cyim --write` | **0** | 100 | 475 |
| `cyim --replace` | **0** | 100 | 475 |
| `cyim --batch` | **0** | 100 | 475 |

This also made a **documented guarantee false**. `CLAUDE.md` § Consumers
says of `--batch`: *"Atomic — failure mid-batch leaves FILE untouched on
disk."* True for a logical mid-batch failure (a pair whose OLD is not
unique), false for a write failure: the file is opened `O_TRUNC`, so by
the time the write fails the original is already gone.

**Severity.** Not privilege escalation, so not CRITICAL by cyim's scale.
HIGH because it is trivially reachable (any full filesystem), completely
silent, destroys user data, and lands hardest on the `daimon` consumer
surface where the exit code is the *only* feedback an agent gets.

**Fix.** New `_buf_write_all(fd, ptr, len)` loops until every byte is
written, treats `w == 0` as `-EIO` (no forward progress — retrying hangs),
and returns negative on failure. `buf_save_file` now also `fsync`s and
checks `close`, because some filesystems (NFS most visibly) only surface
a write error at one of those two points. **After the fix all three verbs
exit 1 with `save failed` on stderr**, and an unconstrained write is still
byte-exact.

**Residual R-1: the save is still not atomic.** See § 5.

### F-2 — `.cyimrc` palette values are not range-checked, and reach a buffer index (**MEDIUM**) — FIXED

`docs/guides/cyimrc.md` and `src/cyimrc.cyr`'s own header both state that
a palette value is *"a 0..255 256-color index, or -1"*. Nothing enforced
it. `_cyimrc_apply` stored whatever `_cyimrc_parse_int` returned, and the
value flowed:

```
.cyimrc  ->  _cyimrc_apply  ->  cyimrc_palette(kind)
         ->  theme_token_color(kind)   ->  _render_emit_fg(buf, off, code)
         ->  _render_u16_ascii(buf, off, n)      # docstring: "0..999"
```

`_render_u16_ascii` fills an 8-byte scratch **backward from index 7**, so
its real precondition is "at most 8 digits". `palette.keyword =
999999999999999` (15 digits) drove the index to **-8** — a stack write
*below* the buffer — and returned 15, so `_render_emit_fg` wrote
`8 + 15 + 1 = 24` bytes into the **12 bytes `render_build_line` reserves
for a colour escape**, putting the render past the caller's `out_max`.

**Measured before the fix:** `render_build_line(..., out_max=120)`
returned `pos = 122` — a 2-byte overflow of the caller's buffer, growing
with digit count and with how close `pos` sits to the reserved tail.

**Severity.** MEDIUM, not HIGH, and the reasoning matters: an out-of-bounds
write is normally HIGH, but the overflow magnitude here is small and
bounded by digit count, the attacker controls the *length* of the
overrun far more than its content, and the two live sinks (`out[8192]`
in `render_line`, the naked variant in the window path) have slack. It
is not a *reliable* corruption primitive. It is still an out-of-bounds
write driven by a file cyim reads from the current directory.

**Fix, two layers.**

1. **At the trust boundary** — `_cyimrc_palette_valid` rejects anything
   outside `-1` and `0..255`, checked once before the ten-key dispatch so
   an eleventh key cannot forget it.
2. **At the sink** — `_render_u16_ascii` clamps `n` into `0..999` itself.
   This is the layer that makes the caller's 12-byte reservation *true*
   rather than *true-if-someone-else-checked*. Clamped, not refused: this
   is a display path, and drawing the wrong colour beats refusing the line.

**See also the ADR gap in § 6** — the interesting half of this finding is
not the arithmetic, it is *whose* input `.cyimrc` is.

### F-3 — render scratch buffers are bounded by terminal geometry, not by their own size (**LOW**, latent) — FIXED

Two fixed stack buffers had the terminal's reported width as their only
write bound:

| site | buffer | bound before | bound now |
|---|---|---|---|
| `_render_cmdline` | `line[2048]` | `pos < cols - 1` | `min(cols - 1, 2048)` |
| `_render_leaf_status` | `sbuf[1024]` | `visible < rw` | also `pos < 1024 - 8` |

`ws_col` is a `u16`, so a terminal is free to claim 65535 columns. Bounding
a 2048-byte stack buffer by that value alone is a ~63 KB stack overflow
waiting for the input that supplies it.

**LOW because it is latent, not live.** On Linux/macOS `scr_cols` is a
hardcoded `DEFAULT_COLS = 80` — `tty_winsize` is consulted **only** under
`CYRIUS_TARGET_AGNOS`, where the value comes from the framebuffer console
and is small. Nothing today can drive `cols` past 2049.

**It is filed and fixed anyway because the feature that makes it live is
on the roadmap.** "Resize-aware editor rendering" has been a named future
item since 1.7.4, and it consists precisely of wiring `tty_winsize` into
`scr_cols` on Linux. The day that lands, these two buffers become
remotely-shaped by whatever the terminal claims. Catching it *before* the
feature is the whole point of an audit pass.

### F-4 — `_cmd_ls_put_int`'s scratch holds 16 of the 19 digits an i64 can produce (**LOW**, unreachable) — FIXED

`var tmp[16]` with a reverse-fill loop bounded by `val`, not by the
buffer. Callers pass buffer-registry indexes, so it cannot be reached
today. Sized to `tmp[24]`.

Recorded rather than waved off because it is **the same
slot-vs-domain mistake that made `cyim-lsp`'s `var argv[4]` a live bug**
(BUG-002) — found here by looking for the *shape* rather than for the
symptom.

---

### F-5 — `_cyimrc_parse_int` wraps i64 instead of rejecting absurd input (**LOW**) — FIXED

`v = v * 10 + d` with no digit cap. A 23-digit run silently wrapped:
`12345678901234567890123` parsed to **4807115922877859019**. Compounding
with F-2, a wrapped value can land *inside* a range check and be accepted
as legitimate — a config value nobody could type on purpose becoming a
plausible one. Digits are now capped at 9 and over-long runs are rejected
like any other malformed value.

### F-6 — `CLAUDE.md` asserted a path-validation control that ADR 0001 explicitly declines (**INFO**) — FIXED

`CLAUDE.md` § Security Hardening item 6 read:

> **No path traversal** — `:e <path>` validates; no `../` escape from
> project root in restricted mode

None of that exists, and per
[ADR 0001](../adr/0001-trust-model.md) none of it is *supposed* to:
cyim is an interactive editor for one local user, not a privilege
boundary, and the ADR states plainly that cyim "doesn't validate paths,
doesn't sandbox config files." There is no restricted mode.

A checklist item describing a control that was never built is worse than
no item: it makes every future audit tick a box that has nothing behind
it. Rewritten to point at ADR 0001 as the authority, to record what the
line used to claim, and to state what the audit should actually check
here — that no path builds a fixed-size buffer write without bounds, and
that the trust model still holds for the surface in question.

### F-7 — the render path is byte-oriented, and that is a decision, not an oversight (**INFO**, accepted)

`render_ctrl_substitute` substitutes C0 (`0x00`–`0x1F`, Tab excepted) and
DEL. It passes `0x80`–`0x9F` through, which in a terminal running 8-bit
controls are the C1 set — `0x9B` being CSI.

**Deliberately not "fixed", because the obvious fix is wrong.**
`0x80`–`0x9F` overlaps the UTF-8 continuation-byte range `0x80`–`0xBF`:
substituting them blind would mangle every non-ASCII character in every
file. Doing it correctly requires decoding UTF-8 in the render path,
which cyim does not do — the renderer is byte-oriented by construction,
one buffer byte to one column.

Recorded as an architectural fact with a real consequence: C1 pass-through
and the absence of double-width/combining-character handling are the same
decision, and both change together if cyim ever grows a codepoint-aware
renderer. Modern terminals are overwhelmingly UTF-8 and render a lone
`0x9B` as a replacement glyph, so exposure today is small.

## 4. What was checked and found clean

Recorded so the next pass knows what has already been walked.

- **Buffer safety, 64-bit access** — every `var NAME[N]` in `src/`,
  `tests/`, `fuzz/` later read or written via `load64`/`store64`, against
  its maximum written offset. **0 findings** (the BUG-002 shape).
- **Marks** (`src/marks.cyr`) — `_marks_global[416]` is 26 × 16 B, and
  both `marks_set_global` and `marks_get_global` range-check the key to
  `'A'..'Z'` *before* indexing. `marks_set` likewise for `'a'..'z'`. Clean.
- **`:ls` rendering** — `_cmd_ls_put_cstr` / `_cmd_ls_put_byte` bound
  every store against `_CMD_LS_BUF_SIZE` while still advancing `pos`, and
  the final NUL is written at a clamped offset. Correct defensive shape.
- **`render_build_line` / `_naked`** — the `out_max - 6` (resp. `- 4`)
  tail reservation exactly covers the unconditional reset + CRLF. Correct
  by construction *given* an in-domain colour code, which is what F-2
  restores.
- **CLI input** — `_cli_drain_stdin` reads 4096 into a 4096 buffer;
  `_cli_match_at` bounds-checks `pos + nlen` against `buf_len`. Clean.
- **Syscall surface** — 234 raw `syscall(...)` sites in `src/`, of which
  **226 are `syscall(1, ...)` (write to stdout/stderr)**. The remaining
  eight: `readlink` (89, grammar-dir resolution), `nanosleep` (35,
  `tty_probe`), `lseek` (8, `_cmd_file_size`), and four agnos-gated calls
  (`kbscan#42`, `sleep_ms#41`, `read#5`). Unchecked write returns on the
  render path are accepted — there is no recovery for "the terminal did
  not take our bytes", and it matches darshana's documented posture. The
  *file* write path is F-1 and is now checked.
- **Command injection** — no `sys_system`, no `/bin/sh`, no raw
  `execve`/`fork` anywhere in `src/`. Enforced by the CI security job.
  Refusal §0 holds.
- **Modeline RCE** (the vim CVE class) — cyim has no modeline, no
  embedded scripting, and does not parse buffer content for commands.
  Refused by architecture, per `CLAUDE.md`'s load-bearing constraint.
- **Escape-sequence injection from file content** — closed at M6 (F-1)
  by `render_ctrl_substitute` and guarded by a CI grep; still in place,
  with the C1 caveat at F-7.

## 5. Residuals — recorded, not fixed

### R-1 — the save path is still not atomic — **CLOSED at v1.8.4**

> **Closed 2026-08-23 by [ADR 0006](../adr/0006-atomic-save.md), shipped as
> v1.8.4.** Saving is now atomic by default — sibling temp, `fchmod` to the
> target's mode, write, `fsync`, `rename`, `fsync` the parent directory — with
> an enumerated in-place fallback for the file shapes where rename would break
> something the user relies on more (symlinks, hardlink sets, non-regular
> files, foreign-owned files, non-writable directories, agnos). Verified: a
> failed write under `RLIMIT_FSIZE` now leaves the original bit-for-bit
> intact across all three write verbs, with no temp left behind. The analysis
> below is retained as the record of why the obvious fix was not taken at
> 1.8.3.

`buf_save_file` opens `O_TRUNC` and writes in place, so a failure part
way through leaves a truncated file. F-1 fixed the *reporting* — the
caller is now told, keeps the modified flag, and exits non-zero — but
the damage is still done.

The stdlib already has the fix in `file_write_atomic` (temp file, fsync,
rename). **Not adopted here, deliberately**: rename changes the inode on
every save, which breaks hardlinks, discards the target's existing
permissions and ownership, and fails where the user can write the file
but not create a sibling in its directory. It is also a direct change to
[ADR 0001](../adr/0001-trust-model.md) § 3, which *accepts*
write-in-place TOCTOU semantics on the grounds that they match vim's
default.

That is an ADR-level decision, not a hardening tweak. The honest state:
**cyim's save is as atomic as vim's default, which is to say not**, and
this is now written down where a future cut can weigh it — including the
option vim actually takes, a `backupcopy`-style choice rather than one
fixed behaviour.

### R-2 — the dead-code floor is 20, and most of it should stay

`CYRIUS_DCE_VERBOSE=1` reports 20 cyim-side functions unreachable from
`main`. Down from 22 at the 1.6.8 closeout. Deliberately not deleted:

- **Frozen plugin ABI** (`plugin_list_*`, `plugin_register_normal_key`,
  `plugin_last_diags`) — [ADR 0004](../adr/0004-plugin-abi-freeze.md)
  forbids removal for the 1.x line whether or not cyim itself calls them.
- **Test/fuzz introspection** (`buf_cap`, `buf_gap`, `editor_last_error`,
  `lang_index`, `lang_is_valid`, `marks_count`, `visual_selection_hi/lo`,
  `window_count_leaves`) — reachable from the harnesses, not from `main`.
- **Documented-deferred config** (`editor_cfg_tabstop`,
  `editor_cfg_line_numbers`) — stored, not yet rendered, per
  [`cyimrc.md`](../guides/cyimrc.md). F-8 fixed the one doc page that
  disagreed.

A DCE report is not a dead-code list for a project with a frozen ABI and
an out-of-line test harness. Recorded as a floor, not a backlog.

## 6. ADR gap — `.cyimrc` is the *directory's* input, not the user's

[ADR 0001](../adr/0001-trust-model.md) says:

> every path the user types, every `.cyimrc` it loads is trusted to the
> degree the invoking shell trusts the user.

`cyimrc_load()` loads **`./.cyimrc`** — cwd-relative. So the file is not
necessarily authored by the user at all: it arrives with whatever
directory they happen to `cd` into. Clone a repository, open a file in
it, and you have executed that repository's configuration choices.

This is the exact shape of vim's `.exrc` problem, which vim answers with
`set exrc` + `set secure` — off by default, and constrained even when on.
ADR 0001's "the user is trusted" framing does not reach it, because the
input is not the user's.

**Two things follow, and only the first is done.**

1. **The memory-safety half is not a trust question at all** and is fixed
   at F-2. A trust model can say "any colour the config names is
   allowed"; it cannot say "an out-of-range integer may corrupt the
   render buffer." Fixed regardless of how the policy question lands.
2. **The policy half is open.** Whether a cwd-relative config should be
   loaded at all — unconditionally, behind a flag, only from `$XDG_CONFIG_HOME`,
   or with a vim-style `secure` restriction — is an ADR decision, not an
   audit finding. Filed as
   [ADR 0005](../adr/0005-cyimrc-cwd-trust-boundary.md), status
   **Proposed**, with the options and their costs.

Worth stating plainly: today's `.cyimrc` surface is ten colour indexes
and three stored-but-unrendered integers. The blast radius of a hostile
config is *a wrong colour*. The reason to settle this now is that the
config surface is scheduled to widen — `cyimrc.md` names keymaps as an
M4 candidate — and a keymap is a very different thing to accept from a
directory you just cloned.

*usually* catches the regression.
